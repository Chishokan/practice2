# 『貸出は三日まで』 設計書

> 一見、和やかな図書館運営ゲーム。
> その実、書架から本を降ろすたびに、世界から何かが消えていく。

---

## 1. コンセプト

### 表の層（プレイヤーが最初に見るもの）

古い図書館に着任した新任司書。訪れる人々の相談に乗り、書架から一冊を選んで手渡す。喜ばれる。評判が上がる。棚が手狭になったら、古い本を地下書庫へ降ろして整理する。

軽く、温かく、少しユーモラス。

### 裏の層（機構）

- 書架から降ろした本の**内容は、現実世界から消える**
- 序盤、整理は単なる作業として提示される。意味は一切説明されない
- 書架の容量は有限。新しい本を受け入れるには、必ず何かを降ろす

### 一行コンセプト

**プレイヤーが「良い司書」であろうとするほど、世界が痩せていく。**

### 設計上の絶対規則

1. **説明しない。** 真相はテキストで語らず、「ズレ」として置く
2. **プレイヤーに「自分の記憶違いかも」と疑う余地を残す。** 断定した瞬間に怖さが死ぬ
3. **序盤の整理作業に意味を持たせない。** 後から遡って意味が生じる構造にする
4. **和やかさを削らない。** 不気味さは、暗い場面ではなく和やかな場面の綻びから立ち上がる

| エンディング | 通常4 + 真エンド1 |

### 章ごとの温度設計

| 章 | 表の空気 | 綻びの density |
|---|---|---|
| 第1章 | 完全に和やか。日常の相談ごと | 気づけない程度に1〜2箇所 |
| 第2章 | 少しずつ噛み合わなくなる | 気づく人は気づく |
| 第3章 | 表層が保てなくなる | 隠さない |

## 3. コアループ

```
来訪者が来る
  ↓
要望を聞く（テキスト）
  ↓
蔵書を検索・選択
  ↓
手渡す / 断る
  ↓
反応（渡した本によって分岐）
  ↓
新しい本が図書館に届く
  ↓
書架が満杯 → 「整理」を要求される
  ↓
降ろす本を選ぶ  ← ここが本作の核心
  ↓
（世界が静かに変わる。プレイヤーには見えない）
```

## 4. データモデル

シナリオは **TypeScript で記述する**（JSON/YAMLではなく）。
理由：伏線フラグの参照ミスがコンパイル時に検出されるため。分岐作品では致命的な差になる。

```ts
type BookId = string;
type VisitorId = string;
type FlagId = string;

export interface Book {
  id: BookId;
  title: string;
  author?: string;
  category: 'history' | 'magic' | 'story' | 'record' | 'unknown';
  /** 書架で見える説明。嘘は書かないが、全ては書かない */
  summary: string;
  /** この本が消えた後に、世界に起こること */
  erasureEffects?: ErasureEffect[];
  /** 消えた後にのみ開示される事実。プレイヤーが真相に至る材料 */
  hiddenNote?: string;
  /** 消えると特定の来訪者ルートが封じられる */
  gatesVisitors?: VisitorId[];
}

export interface ErasureEffect {
  /** 街の描写テキストの差し替え、来訪者の記憶欠落、など */
  kind: 'townDescription' | 'visitorAmnesia' | 'ledgerRewrite' | 'searchBlock';
  payload: string;
}

export interface Visitor {
  id: VisitorId;
  displayName: string;
  chapter: 1 | 2 | 3;
  order: number;
  /** 来訪の条件（フラグ／消去済みの本／周回数） */
  conditions?: VisitorCondition;
  scenes: Scene[];
  /** 要望に応え得る本。複数正解を許す */
  acceptableBooks: BookId[];
  /** 本ごとの個別反応。未定義なら generic にフォールバック */
  reactions: Partial<Record<BookId, Scene[]>>;
  genericAcceptScene: Scene[];
  refuseScene: Scene[];
  flagsOnResolve: FlagId[];
}

export interface WorldState {
  cycle: number;                 // 周回数
  chapter: 1 | 2 | 3;
  shelf: BookId[];               // 書架にある本
  shelfCapacity: number;
  erasedBooks: BookId[];         // 周回を跨いで累積する（重要）
  flags: Set<FlagId>;
  anomalyLevel: number;          // 0-4
  ledger: LedgerEntry[];         // 貸出台帳。改変対象
  reputation: number;
}
```

### 周回引き継ぎの原則

**`erasedBooks` だけが周回を跨いで永続する。** その他は初期化。

- 1周目に降ろした本は、2周目の書架に**最初から存在しない**
- 周回するほど図書館は貧しくなり、救えたはずの来訪者を救えなくなる
- 「何周もして全分岐を見る」ことに代償を課す設計

## 5. 綻びシステム（本作の演出の生命線）

`anomalyLevel` に応じて、UI層に静かな異常を注入する。
**すべて演出であり、システムメッセージは一切出さない。**

| Lv | 発現 | 実装 |
|---|---|---|
| 0 | なし | — |
| 1 | 貸出台帳の一行が、プレイヤーの記憶と食い違う | `ledger` の過去エントリを書き換え |
| 1 | 常連が、前回借りた本の話をまったくしない | 会話分岐の抑制 |
| 2 | 窓外の街の描写が、少しずつ簡素になる | `townDescription` の段階的短縮 |
| 3 | 序盤に会った来訪者が「初めまして」と訪れる | `visitorAmnesia` |
| 4 | 検索しても出ない。でもプレイヤーは確かに見た | `searchBlock` |

### 実装方針

```ts
interface AnomalyRule {
  threshold: number;
  once: boolean;
  apply: (state: WorldState) => WorldState;
}
```

宣言的なルール配列として持ち、章遷移時と整理実行時に評価する。
**ハードコードした演出をシーンに埋め込まないこと。** 周回で組み合わせが変わるため。

## 6. エンディング

| ID | 名称 | 条件 | 性質 |
|---|---|---|---|
| E1 | 良き司書 | 全来訪者を満足させる | **最も多く消した = 最悪の結末** |
| E2 | 空の書架 | ほとんど渡さなかった | 誰も救えないが、世界は残る |
| E3 | 閉架 | 真相に到達し、図書館を閉じる | |
| E4 | 継承 | 台帳を次の司書に遺す | 2周目への導線 |
| TRUE | 最初の一冊 | 複数周回を通じ、特定の一冊を守り抜く | |

E1が最悪の結末である点が本作の反転の核。
**プレイヤーは1周目でほぼ確実にE1に到達する。** そう設計する。

## 7. ビジュアル方向

### 制作順序（厳守）

矩形プレースホルダで全実装 → シナリオ確定 → **最後に画像を差し込む**。
逆順は、設定変更のたびに画像を作り直す地獄になる。

### 画像アセット

| 種別 | 枚数目安 | 用途 |
|---|---|---|
| 立ち絵 | 18（来訪者ごと1枚） | 差分は当面なし |
| 背景 | 5（閲覧室 / 書架 / 地下書庫 / 窓辺 / 夜の館内） | |
| イベント一枚絵 | 8〜10 | 章の節目・エンディング |

### カラートークン

夜の図書館、ランプ一灯。**暖色クリーム地は使わない**（陳腐かつ本作の温度ではない）。

```css
--ink:        #14100D;  /* 墨。基本文字色 */
--dark:       #12171A;  /* 書架の闇。背景 */
--parchment:  #D6CDB4;  /* 羊皮紙。カード面にのみ使用 */
--lamp:       #E8A64B;  /* 灯火。唯一の暖色アクセント */
--moss:       #4A6B5A;  /* 苔緑。UI構造線 */
--erasure:    #6B5B7A;  /* 消失の紫。第2章まで一切登場させない */
```

`--erasure` は**演出上の切り札**。序盤に一度も見せないことで、初出時に効く。

### タイポグラフィ

| 役割 | 書体 |
|---|---|
| 見出し | Shippori Mincho B1 |
| 本文 | Zen Old Mincho |
| 台帳・数値 | M PLUS 1 Code |

### シグネチャ要素

**貸出台帳。** UI全体を一冊の台帳として構成する。
そして台帳の記述が、プレイヤーの知らないうちに書き換わる。
本作が記憶される一点はここ。他の装飾は徹底して静かに保つ。

## 8. 技術スタック

| 領域 | 採用 | 理由 |
|---|---|---|
| ビルド | **Vite** | 起動・HMRが速い。短時間開発で効く |
| UI | **React 18 + TypeScript** | |
| 状態管理 | **Zustand** | Reduxは重く、Contextは再描画が厳しい |
| スタイル | **Tailwind CSS** | |
| 演出 | **Framer Motion** | テキスト表示・フェード |
| シナリオ | **TypeScript定義ファイル** | 型でフラグ参照ミスを検出 |
| セーブ | **localStorage** | 周回データは別キーで永続 |
| 配布 | **Cloudflare Pages** | 静的出力・無料・独自ドメイン可 |

Next.jsを採用しない理由：SSR・ファイルルーティング・サーバー機能が単一画面のゲームには余剰。設定量とビルド時間が増えるのみ。

## 9. ディレクトリ構成

```
src/
├── main.tsx
├── App.tsx
├── domain/                 # ルールのみ。Reactに依存させない
│   ├── types.ts
│   ├── worldState.ts
│   ├── shelf.ts            # 書架の追加・降ろす
│   ├── erasure.ts          # 消去の波及処理
│   ├── anomaly.ts          # 綻びルール
│   └── endings.ts
├── store/
│   └── gameStore.ts        # Zustand
├── content/                # シナリオデータ（テキスト作業はここだけ）
│   ├── books/
│   │   ├── chapter1.ts
│   │   └── index.ts
│   ├── visitors/
│   │   ├── ch1-01-<name>.ts
│   │   └── index.ts
│   └── anomalies.ts
├── ui/
│   ├── screens/            # Reception / Shelf / Archive / Ledger
│   ├── components/
│   └── theme.css
└── save/
    └── persistence.ts
```

### 設計上の要請

`domain/` は純粋関数のみで構成し、Reactに一切依存させない。
理由：分岐とフラグのテストが書けるようになり、伏線の破綻を自動検出できる。
本作の規模では、これが完成できるかどうかを分ける。

## 11. リスクと対策

| リスク | 対策 |
|---|---|
| **執筆量で失速する**（最大のリスク） | Phase 4以降は「1日1来訪者」に固定。実装作業と混ぜない |
| 綻びが伝わらない | Phase 2完了時に第三者にプレイさせ、気づくかを確認 |
| 逆に序盤からバレる | 第1章の綻びは2箇所まで。増やしたくなっても増やさない |
| スコープ膨張 | 立ち絵の差分・音声・実績は**すべて禁止**。1周目リリースでは実装しない |
| 分岐の破綻 | `domain/` の純粋関数に対し、全ルート到達可能性のテストを書く |
